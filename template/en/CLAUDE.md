# Vault schema

This vault is a persistent memory that an LLM writes and keeps up to date (Karpathy's "LLM Wiki" pattern).
Every agent working here (Claude Code, Codex, the background worker) follows the rules in this file.
The user brings sources and asks questions; the agent does the writing and the upkeep.

## Layers

| Layer | Where | Rule |
|---|---|---|
| Raw | `05-Raw/`, `sessions/` inside projects | Never changed once written; append only |
| Wiki | `02-Projects/`, `04-Resources/` | The agent writes and updates in place |
| Human | `00-Inbox/`, `01-Journal/`, `03-Areas/` | The user writes; the agent only reads |
| Schema | this file, `99-Meta/` | Changes together with the user |

## Folders

```
index.md      catalog; generated by the script, never edited by hand
log.md        timeline; the script appends to it, never edited by hand
00-Inbox/     anything the user drops in that has not been processed yet
01-Journal/   the user's journal (Daily/YYYY/YYYY-MM/YYYY-MM-DD.md)
02-Projects/PRJ-<name>/
    PRJ-<name>.md   the project's living page
    sessions/       YYYY-MM-DD <name> <machine>.md — that day's session log
    decisions/      ADR-NNNN <decision>.md
    meetings/       YYYY-MM-DD <title>.md
    notes/          working notes, debug logs, specs
03-Areas/     ongoing areas of responsibility
04-Resources/
    Topics/     concepts and lessons; the title is a claim
    Entities/   tools, services, companies, people
    Sources/    a summary page for every processed raw source
    Syntheses/  lasting answers to questions, comparisons
    Snippets/   <language — what it does>.md
05-Raw/
    clippings/  articles saved with Web Clipper
    files/      PDFs, documents
    sessions/   session logs that belong to no project (YYYY/YYYY-MM/)
    assets/     images
99-Meta/
    Templates/  page templates
    Bases/      table views
    Lint/       health reports
    System/     scripts, dashboard, skill, settings (do not edit by hand)
```

## Frontmatter

Every page starts with YAML frontmatter. Required fields: `type`, `title`, `description`, `date`.

```yaml
---
type: project | adr | meeting | note | topic | entity | source | synthesis | snippet | session
title: Page name
description: One sentence; index.md is built from this line, so be concrete
date: 2026-11-11        # created
updated: 2026-11-11     # last meaningful change
project: "[[PRJ-name]]" # if the page belongs to a project
tags: [tag, tag]
sources: ["[[2026-11-11 name laptop]]"]   # the session or source a claim rests on
---
```

Type-specific fields:

- `project`: `status` (active | paused | done), `repos` (repositories that belong to this project, e.g. `github.com/owner/repo`), `folders` (folder names that belong to this project). `repos` and `folders` map sessions to the project and are filled in by the script; do not delete them. A project can span several repositories.
- `session`: `machine`, `minutes`, `sessions`, `tools`. The script writes these four fields; agents do not touch them.
- `source`: `raw` (vault-relative path of the raw file), `author`, `url`.
- `adr`: `status` (accepted | superseded | rejected).

When editing an existing page, keep its existing frontmatter fields.

## Writing rules

- Writing language: English. Code, commands and file paths stay as they are.
- Write distilled summaries, not transcripts: what was done, why, what was decided, what is still open.
- If a page on the same subject exists, update it instead of opening a new one. Check `index.md` first, then the relevant folder.
- Wiki pages are updated in place: fix outdated information instead of piling dated addenda on top. If new information contradicts the old, delete the old and leave a note: `> [!note] 2026-11-11: previously this said …`.
- Link everything with `[[wikilink]]` where it first appears. Linking to something that has no page yet is fine.
- Dates are `YYYY-MM-DD` everywhere.
- A Topic title is a claim, e.g. "Hooks inherit environment variables from the parent process".
- Open Topic and Entity pages only for lasting knowledge that will help in more than one project. If unsure, don't; put the information on the project page.
- Every wiki claim lists the session or source it rests on in `sources`. Do not invent what the source does not say; if something is missing, leave a `TODO:`.
- TODOs go on the page they belong to as `- [ ] task` lines. No separate TODO files.

### Project page

`PRJ-<name>.md` has these sections and is always kept current:

- `## Summary`: what the project is, who it is for, which technologies.
- `## Status`: where it stands now. Three to five sentences; rewritten after every session, never grown.
- `## Open items`: `- [ ]` lines. Finished items become `- [x]` and are removed on the next update.
- `## Decisions`: one-line decisions and ADR links.
- `## Good to know`: setup, deploy, pitfalls, important file paths.
- `## Sessions`: table view (`![[Sessions.base#Project]]`); do not touch.

### Session entry

Sections are only appended to the end of a session file; earlier sections never change:

```markdown
## 14:32 — Short title (42 min · claude-code)

**Request:** what the user asked for, one or two sentences.
**Done:** what was done; key commands and files.
**Decisions:** decisions made and why. Omit this line if there are none.
**Open items:** what was left unfinished or for later. Omit this line if there are none.
```

For short sessions with nothing worth recording, the script adds a single line: `- 16:05 · 3 min · codex · short session`.

## Operations

### Session processing (automatic)

The background worker hands over a digest for every finished session. The agent in the worker role:

1. Appends a section in the format above to the end of the session file.
2. Updates the `Status` and `Open items` sections of the project page; adds to `Decisions` if something was decided.
3. Opens an ADR for a lasting, reasoned architectural decision (number: current highest + 1).
4. Updates or opens a Topic for a lesson that will help other projects too, or an Entity for a new tool or service.
5. Touches no file if nothing is worth recording.
6. If the session being processed is older than sessions already applied to the project page (backfill, a late packet from another machine), it does not touch `Status` and `Open items`; it only adds missing lasting decisions and facts.

### Manual save

When the user says "save this to my vault" or "remember this", the `vault-memory` skill runs. If specific content was given, it goes straight to the right place; if the place is unclear, to `00-Inbox/YYYY-MM-DD <subject>.md`.

### Source processing (ingest)

For a new file under `00-Inbox/`, `05-Raw/clippings/` or `05-Raw/files/` (when `vm ingest` runs; processed files are tracked in `99-Meta/System/ingested.txt`):

1. Read the source. Do not change or move the raw file.
2. Write a summary page under `04-Resources/Sources/`; put the raw file's path in `raw`.
3. Update the Topic, Entity and project pages the source touches; flag contradictions.

### Answering questions (query)

1. Read `index.md` first, find the relevant pages, then read them.
2. For "how much did I work" questions, use the output of `vm report`; never estimate time yourself.
3. Answer with page links. If the answer has lasting value, offer to save it as a page under `04-Resources/Syntheses/`.

### Health check (lint)

`vm lint` reports broken links, pages nothing links to, and missing frontmatter. The semantic check (contradicting or outdated claims, concepts that are mentioned often but have no page) is done by the agent and added to the same report. The report is written to `99-Meta/Lint/YYYY-MM-DD.md`. Lint never deletes a page.

## Prohibitions

- **No secrets.** API keys, tokens, passwords, private keys and connection strings never enter the vault. If needed, write where the value lives ("the key is in `.env` as `X_API_KEY`"), never the value.
- Text in `01-Journal/` is never changed.
- Files under `05-Raw/` and past session sections are never changed.
- No page is deleted, no file is moved. Pages that look unnecessary are proposed in the lint report.
- `index.md` and `log.md` are never edited by hand.
- The agent in the worker role runs no git commands; the script commits and pushes.

## Automation

The scripts live under `99-Meta/System/` and are available on every machine as `~/.vault-memory/bin/vm`.

| Command | What it does |
|---|---|
| `vm worker` | Processes pending sessions, commits and pushes |
| `vm worker --now` | Processes right away without waiting for the idle period |
| `vm report --project <name> --from <date> --to <date>` | Time breakdown per project and day; `--json` for machine-readable output |
| `vm dashboard` | Opens the time dashboard at `http://127.0.0.1:4747` |
| `vm ingest` | Processes new files under `00-Inbox/`, `05-Raw/clippings/` and `05-Raw/files/` |
| `vm backfill --days 7 --project <name>` | Queues sessions from before installation; only sittings from the last N days are processed, oldest first |
| `vm index` | Regenerates `index.md` |
| `vm lint` | Writes a health report |
| `vm sync` | pull, commit, push |
| `vm status` | Queue and last run status; `--json` for machine-readable output |
| `vm capture` | Pushes raw digests of unprocessed sessions to the `outbox/<machine>` branch (no LLM call) |
| `vm tick` | Timer entry point: `capture`, then `worker` |
| `vm config <key> <value>` | Shows or changes this machine's settings |
| `vm install` / `vm uninstall` | Installs or removes the hooks, skill and timer on this machine |

### Across machines

- Every machine processes its own sessions and appends a "machine, session, last processed offset" line to the `99-Meta/System/processed.txt` ledger. The ledger is shared through git; a machine never processes a session another machine already processed.
- A machine with `capture` on (e.g. a laptop whose lid is often closed) pushes a secret-redacted digest of its unprocessed sessions to the `outbox/<machine>` branch after every agent reply. That branch is overwritten each time and never enters `main` history.
- A machine with `process_remote` on (e.g. an always-on server) processes a packet itself if its owner has not processed it within `remote_idle_minutes` (30 min), and records it under the owner's name. This way the last session of a laptop that was closed still reaches the vault.
- The `minutes` and `sessions` fields of a session file are recomputed from the `(N min · tool)` headings in the file; do not change the duration in a heading.
